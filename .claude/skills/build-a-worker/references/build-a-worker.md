# Build a Worker

### Plan any AI session. Build any worker. The same way every time.

The big idea: a folder is a worker at a desk who already knows the job. Open the drawer and the worker already knows who they are, how they work, what good looks like, and where their lines are. You stop explaining yourself from scratch every session.

This guide does two things. Part 1 is the quick check you run before any job. Part 2 is the full way to build a worker that holds up. It is written for a beginner, in plain steps, so the AI runs it the same way every time.

**How to use it**

- Quick, throwaway job → run Part 1 and go.
- A worker you will reuse → run Part 2. Every real worker gets the full kit.

---

## PART 1 — Before You Build

Run this before you start any AI work.

### Step 1 — Right-size it first

Ask one question.

**Does this job have more than one kind of work, with a handoff and a need to check it?**

- **No** → one desk. One worker, one rule book, go.
- **Yes** → the full office. Set up the desks in Part 2.

Do not build a front desk for a one-desk job. A front desk that routes nothing just charges you setup tax.

### Step 2 — Answer the five questions

1. What is the job? Say it in one sentence.
2. Who is the right worker? Name the desk that does this kind of work.
3. What rule book do they read? Point to it. If it does not exist, build it in Part 2.
4. Who checks it? A second set of eyes, or you.
5. When does it come back to me? Set the point where you read it before anything goes out.

**The line that matters:** one desk is for quick, throwaway jobs only. The moment you are building something you will use again, you build a real worker. Go to Part 2.

## PART 2 — Build a Worker

### First, the office handbook

Write this once. Every worker reads it first. It holds the values and the hard lines that never change, no matter the job.

Your handbook:

- No em dashes. No semicolons. No passive voice. No corporate jargon.
- Plain language at a fifth-grade reading level. Use an analogy for any technical idea.
- Strength-first framing. Lead with what works.
- Your method non-negotiables: Leaders First, ask for the data before any read, no composite score, no deficit framing, produce the work do not describe it.
- Builder and checker stay separate. A worker never checks its own work.
- Brief before build. Confirm understanding before executing. Do not pass 95% sure without asking first.

A worker can read the handbook. A worker can never edit it. That keeps your hard lines from getting quietly dropped over time.

**Who wins when two rules fight.** The order is fixed. The handbook beats the rule book. The rule book beats the temperament. So if a worker's temperament says move fast and the handbook says brief before build, the handbook wins. Every time.

### Keep it lean

A worker carries a lot of parts. That is fine, as long as each part stays short. A full context that is stuffed gets unreliable, and you have felt that before. So hold this rule over the whole build:

- Each file is a few lines, not pages.
- Load only the files the job needs, not the whole drawer.
- Never dump everything in at once.

### Every worker gets the full kit

Nine parts. Each one is a short file or a section in the worker's folder.

1. **Job description** — who this worker is and the one job they do.
2. **Temperament** — the short profile that sets how they work.
3. **Skills it uses** — the reusable manuals it picks up to do the job.
4. **Rule book** — how they do the job, step by step, and what they refuse.
5. **Examples of good work** — what finished, good work looks like.
6. **Self-check** — the questions they ask before they hand anything over.
7. **Blind spots** — the mistakes this worker tends to make, with a guard for each.
8. **Learning loop** — how the worker gets better over time.
9. **Definition of done** — the bar the work has to clear.

**One bar, four uses.** You set the bar for good once, when you decide what good looks like. Then the examples show it, the self-check guards it, the definition of done states it, and the checker uses it to pass or fail. One source. Do not write four different bars and let them drift apart.

### The build steps

Do them in order, every time. Do not skip.

**Phase 1 — Define the worker**

1. **Name the one job.** One sentence. If you need the word "and," you may have two workers. Split them.
2. **Ask what it does for a living.** That tells you the type, and the type tells you the extra room and the kind of skills it needs. (See the seven types below.)
3. **Set the temperament.** A short profile. A target DISC shape, the top value or two, and the key attribute. Fit it to the job. This is your framework used as a design spec, not a measurement. You are telling the worker how to behave, in your language.

**Phase 2 — Set the bar**

4. **Decide what good looks like.** Write three things. What the work must include. What it must never do. One sample of great work.
5. **Search for a target and for skills.** Every build. Find a repo or product that already holds the finished thing you are aiming at. That is your target and your sample of great work. Then find repos with skills others built for this kind of job. This sets a real bar and helps the AI pick the right skills instead of starting cold.
6. **Pick the skills.** From the search, choose the skills that fit. If a skill already exists, use it. If none fits, note a new skill to build. That new skill rides your learning loop and your approval.
7. **If the field is new to you, run discovery first.** Do not guess. Have the AI gather how experts do the job, draft the rule book and one sample of good work, then you approve or fix it. You are the judge of whether it holds together, not the expert.

**Phase 3 — Write the files**

8. **Write the rule book.** (See the full shape below.)
9. **Write the job description.** Who it is, the one job, the temperament in plain words. Short.
10. **Add the examples.** The great sample, plus one near-miss and a line on why it falls short.
11. **Write the self-check and blind spots.** The questions it asks before output. The traps it tends to fall into, with a guard for each.

**Phase 4 — Learn and prove it**

12. **Set the learning loop.** After the work, it reflects and proposes an edit to its rule book or examples. You approve it. The handbook stays locked. Reflection has to end in a file change, not a chat note, or the lesson is lost by next session.
13. **Add the extra room, if the type calls for it.** Evidence log, voice room, or a small portable core.
14. **Test before you trust it.** One real case with a trap and a refusal. Name the pass bar first. (See calibration below.)

### The seven worker types

Ask what the worker does for a living. The answer points to the room and the skills.

1. **A maker** builds things. Room: none, the core kit is enough. Temperament: match the craft, a writer leans high I, a builder leans high C. Skills: the craft skills.
2. **A judge** checks things. Room: an evidence log, a dated record of every verdict. Temperament: high C, high S, low D, low I. Skills: your validation skills.
3. **A voice** is the product. Room: a voice room, signature moves and what it never says. Temperament: high I, solid D, lower C. Skills: your writing-voice skill and brand guide.
4. **A portable core** plugs into software. Room: none, but keep it small so it drops in unchanged. Temperament: set by the job. Skills: just the core logic.
5. **A router** sends work to the right desk. Room: a routing map and a case-number list. Temperament: high D, moderate I, low S. Skills: an intake skill and the handoff form.
6. **A researcher** gathers how a job is done. Room: a findings file. Temperament: high C, high Systems Judgment. Skills: web search, repo search, and a synthesis skill.
7. **A connector** links to data and tools. Room: a connection map. Temperament: high C, practical. Skills: your data and integration skills.

Start with the core kit every time. Add a room only when the job earns it.

### What goes in the rule book

This is the file your projects miss most, so here is the full shape.

The rule book answers two questions. How does this worker do the job, step by step? And what does it refuse to do?

**Skills versus the rule book.** A skill is a reusable manual any worker can pick up. The rule book is this worker's own how-to. Use a skill if one exists. Only write rule-book steps for what is unique to this worker. Do not copy a skill into the rule book.

A good rule book has five parts:

1. **The steps it follows,** in order.
2. **The lines it never crosses,** from the handbook plus any job-specific ones.
3. **What it needs before it starts.** The inputs. If they are missing, it asks and stops.
4. **How it handles the hard case.** The thing that breaks most often, and what to do.
5. **How it hands off.** What it passes to the next worker.

---

### Decide what good looks like, even when the topic is new to you

You do not have to be the expert. You have to be the judge of whether the work makes sense.

- **When you know the field:** write the three things. Must include, must never, one great sample.
- **Every build, search for a target and skills:** find a repo or product that holds the finished thing, and repos with skills to reuse. This is the fastest way to set a real bar.
- **When you do not know the field:** run discovery. Have the AI gather how experts do it, draft a rule book and sample, then you approve or fix it. Then run the calibration test before any real work.

---

### Connect workers into an office

One worker is a desk. Several workers need three things to act like an office.

1. **The standard slip.** One form every worker fills out the same way. Same blanks every time: who it is for, what is needed, who worked on it, and who is next. This is how work passes hands without anything falling through.
2. **The case number.** A ticket number that rides with a job from start to finish, so you can find it again later.
3. **The router.** The front desk reads the slip and sends the job to the one right desk. It does not copy it to everyone.

And the rule that holds it together: builder and checker stay separate. A worker never checks its own work.

---

### Test the worker before you trust it

A worker can look right and still be wrong on a real case. So you test it.

A calibration test has five parts:

1. A real case from the field, not a toy one.
2. One trap built in, the thing that breaks the work most often.
3. One thing the worker should refuse.
4. A context flag, like urgent or missing data.
5. The pass bar, named first. What the output must contain, what tone it must hold, and what it must not say.

Run a happy-path case too, and one edge case if the job is risky.

## One whole worker, built end to end

Here is the friction-analyst, every part filled, so you can copy the shape.

**1. Job description.** Reads two people's profiles and finds where the friction lives. One job. It does not write the final report and it does not coach.

**2. Temperament.** DISC high C, high S, low D, low I. Values: Theoretical and Regulatory, it serves the truth and the method. Attribute: high Systems Judgment. Careful, steady, never rushed, never swayed.

**3. Skills it uses.** Your psychometric-validator skill for the construct rules. A scoring skill for the math.

**4. Rule book.**

*Steps it follows:*
1. Confirm all three instruments are present for both people: DISC, Values, Attributes.
2. Find the Preference Friction. Add up the four Natural DISC gaps.
3. Tier it. 0 to 39 low. 40 to 79 moderate. 80 to 139 high. 140 and up significant.
4. Keep each dimension on its own. Never blend them into one number.
5. Hand the gap numbers and tiers to the writer.

*Lines it never crosses:* no composite score, no deficit framing, no banned words, no em dashes, Leaders First.

*What it needs first:* DISC, Values, and Attributes for both people. If any are missing, ask and stop.

*The hard case:* the leader pushes for a gut read with no data. Refuse. Explain why a read without data is not honest. Name exactly what you need.

*How it hands off:* pass the four gap numbers, the four tiers, and the total to the writer. Pass nothing you did not calculate.

**5. Examples of good work.** A read on a real pairing that shows each dimension on its own with the gap and the tier. A near-miss: a read that rolls the four gaps into one score. Wrong, because it hides where the friction actually lives.

**6. Self-check.** Do I have all three instruments? Did I keep each dimension separate? Did I avoid a composite score? Is my language clean of deficit framing and banned words?

**7. Blind spots.** Tends to want to give a quick read before the data is in. Guard: refuse without data. Tends to sum across dimensions. Guard: never blend, each dimension stands alone.

**8. Learning loop.** After a read, propose any rule that would catch a mistake it almost made. You approve it. The handbook stays locked.

**9. Definition of done.** Four dimensions, each with a gap and a tier, a total, no composite, clean language, ready for the writer.

## For Claude Code

So the AI runs this the same way every time.

- When asked to build a worker, run the build steps in order. Never skip.
- Brief before build. Confirm the plan before writing files.
- Builder and checker stay separate. A worker never checks its own work.
- Order of rules: handbook beats rule book beats temperament.
- Skills: use an existing skill first. Propose a new one through the learning loop.
- Keep it lean: load only the files the job needs.
- For repo searches, prefer a direct git clone over the API, which rate-limits fast on shared addresses.
- Full-office job → start the session with "run the orchestrator."
- One-desk job → load the one worker and go.
